# 010 — Flyway for Database Migrations

## Status
Accepted

## Context
Argus requires a PostgreSQL schema before the system can run, plus historical event data in both PostgreSQL and Qdrant. A decision was needed on how to manage schema initialisation and versioning across environments and repository clones.

## Decision
Flyway Community Edition manages the **relational schema**. Versioned SQL files live in `backend/src/main/resources/db/migration/` and are applied automatically on Spring Boot startup.

Flyway does **not** manage seed data. Loading the 24 historical events is a separate step: `python sidecar/seed/seed.py`.

## Reasoning
Manual schema setup is error-prone and undocumented. Flyway provides versioned, auditable, repeatable migrations — every schema change is a numbered file with a clear history. This is standard practice in BFSI environments where schema changes must be traceable.

Seed data deliberately sits outside migration history, for two reasons:

- **Outcomes are derived, not authored.** The 1d/10d/30d returns are fetched from yfinance at seed time and tagged `VERIFIED` or `UNAVAILABLE` depending on what the provider actually returns. Freezing them into a SQL migration would convert measured data into a hardcoded literal with no provenance.
- **Qdrant has no migration story.** Historical analogues require 768-dimension embeddings generated by `nomic-embed-text`. Flyway speaks SQL to a relational database; it cannot populate a vector store. Splitting seeding across a migration file and a script would leave the two stores able to drift apart.

One script that writes both stores in a single pass is the honest boundary.

## Boot 4 note
Spring Boot 4 split autoconfiguration into per-technology modules. `org.flywaydb:flyway-core` supplies the engine but nothing reads `spring.flyway.*` without `org.springframework.boot:spring-boot-starter-flyway` on the classpath. Without that module Flyway is silently inert — no migration runs and no error is logged, because there is no autoconfiguration present to log one. Both dependencies are required.

## Consequences
- A developer cloning the repo gets the schema created on first Spring Boot startup
- Schema changes are versioned and auditable; `flyway_schema_history` records what ran
- Seeding is an explicit, documented setup step, not automatic — the database is empty until `seed.py` runs
- `seed.py` is therefore a user-facing setup step, not an internal tool
